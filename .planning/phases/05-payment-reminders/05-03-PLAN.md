## Locked Decisions Binding Here

- **D5-02:** watermark suppression — an instant crossed before `remindersEnabledAt` is SUPPRESSED_PREEXISTING; at most the single most-severe eligible touchpoint per schedule ever sends. The sweep writes the suppression rows when it encounters them (sweep-time classification); the settings action (05-04) only stamps/nulls the timestamp. Re-enable moves the watermark forward: anything crossed while off is suppressed.
- **D5-03:** OVERDUE instant is `dueAt + 72h` — dunning cadence independent of the checkout block's strictly-past-due flip (D-04).
- **D5-04:** instant math — DUE_SOON is exactly `dueAt - 3*24h`; no shop-calendar/DST arithmetic in v1.
- **From 05-02's measurements (all binding):** E3 — completed schedule refusal is `success: null` + userErrors code PAYMENT_REMINDER_SEND_UNSUCCESSFUL, message "Payment schedule is already completed", HTTP 200, no top-level errors, idempotent → SUPPRESSED_PAID. N1 — one reminder per ORDER per 24h (same code, message "You cannot send more than 1 payment reminders for the same order in a 24hour period"; proven per-order, not per-company) → the per-order guard + 25h backoff + RATE_LIMITED classification below. N5 — the mutation has no state-flip side effect (dueAt/completedAt/balanceDue never move), so unlike validationUpdate it is a pure side-effecting send. E4 — company-less schedules are accepted (recipient = the order's customer); the ATTRIBUTED filter stays as an explicit product choice. E2 API half green on #1010/#1015; DUE_SOON copy green per the addendum.
