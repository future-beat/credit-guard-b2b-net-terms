## Design decisions (pre-made — do not re-litigate during execution)

1. **Paginated per-company queries, NOT a nested bulk operation.** The candidate bulk document would nest three connection levels (companies → orders → paymentSchedules); the documented bulk limit 02-03 recorded is two levels, and per the gap-closure directive the alternative must be verified, never assumed. Verification here is by construction: the paginated `company(id){ orders(first:250, after) }` shape was VERIFIED WORKING live this session with the current scopes (02-05 SUMMARY § CRITICAL FINDING, remedy 2), while the nested-bulk shape was not. Research already accepts paginated at SMB scale (bulk is cost-exempt, but tens of companies × pages of 250 is negligible quota). Record in the SUMMARY that nested-bulk remains an unprobed future optimization — do NOT probe it in this plan; it changes nothing here and every live probe costs deploy-day risk.
2. **Pull ALL of each company's orders — no financial-status filter.** Settled and cancelled orders contribute zero exposure via the engine's three gates (contributes() in ledger.server.ts), and unfiltered ingestion makes `local count(companyId=X) == Company.ordersCount` a usable reconciliation invariant for 02-08. This supersedes 02-03's pending/partially_paid filter and moots research A7's filter question for the backfill path.
3. **D2C orders no longer enter via backfill** (a company enumeration cannot see them — by definition). They still enter retained-but-excluded via order webhooks (rung 3, UNRESOLVED → NO_COMPANY at reconciliation). Exposure arithmetic is identical either way: a D2C order has never contributed a cent. State this in the backfill header.
4. **The claim/status machine survives; only the work function changes.** The work is now synchronous (no async bulk operation to await), so: startBackfill claims → runs runCompanyBackfill inline within the tracked promise → writes completed/failed. pollBackfillIfStale keeps its role for a run that died mid-way (status running + stale) — it simply re-runs runCompanyBackfill, which is safe because every write is an idempotent upsert or a full recompute.
5. **BackfillState keys are frozen** — scripts/prod-ledger-state.mjs parses this JSON in production and 02-08 clears/reads it over railway ssh. Same keys, same order, status first; operationGid stays as a key and is now always null.
