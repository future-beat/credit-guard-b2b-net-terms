## Locked Decisions

- **D4-03 (user):** ENFC-05 records (a) blocked/unblocked state transitions with exposure/limit/overdue snapshot, (b) leaked orders — an order arriving via orders/create whose company was in a blocked state at ingest. Per-attempt block logging is out of scope by platform fact.
- **P4-L1 (planner lock, state predicate):** a company is in blocked state iff `bypassEnforcement === false AND creditLimit !== null AND (overdue === true OR exposure >= creditLimit)`. Rationale: under D4-01 remaining-credit semantics, `exposure >= limit` means remaining credit ≤ 0, so every positive-total cart is blocked — that is the company-level "cannot place new net-terms orders" state. `exposure == limit` is blocked state (zero remaining credit) even though the Companies page badge reads "Within limit" at that point — the badge reports exposure vs limit, this predicate reports order-blocking; the divergence is deliberate and documented in the predicate's doc comment. Observe-only (limit null) is never blocked state (CRED-04).
- **P4-L2 (planner lock, leak predicate):** an order leaked iff, at attribution time and BEFORE its own exposure contribution is recomputed in, `bypassEnforcement === false AND creditLimit !== null AND (overdue === true OR exposure_pre + order_outstanding > creditLimit)` — the exact D4-01 comparison the Function would have made, using the order's `totalOutstandingSet` as the cart-total proxy (exact for an unpaid net-terms order; an order partially paid at creation understates, which only under-flags — same conservative direction as the rest of the ledger). Currency is uniform store currency server-side (D-07), so no D4-02 mismatch arm exists here. VERIFIER NOTE (F-06): P4-L2 is deliberately BROADER than REQUIREMENTS.md ENFC-05's literal "while its company was blocked" wording — it also flags orders that themselves would have exceeded remaining credit even when the company was not yet in blocked state, because that is the exact comparison the validation Function would have made. Extra BYPASSED_ORDER events beyond the literal wording are intentional coverage, not false positives; the Phase 4 PR (04-05) proposes the matching one-line REQUIREMENTS.md touch-up.
- **P4-L3 (planner lock, event kinds):** `BLOCK_STATE_ENTERED`, `BLOCK_STATE_EXITED`, `BYPASS_ENABLED`, `BYPASS_DISABLED`, `BYPASSED_ORDER` — string constants exported from enforcement.server.ts; the table stores companyGid + companyName snapshots (no FK) so events survive company deletion (the Powderbound lesson: companies get deleted).
