## Inline-Edit Interaction Contract (Credit limit column)

The core interaction of the phase. Prescriptive, end to end:

**Display mode (default, per row):**
- `limit = null` → subdued text **"No limit"** followed by an accent-blue **"Set limit"** link-style control.
- `limit = 0` → **"$0.00"** rendered as the clickable edit affordance (accent link styling).
- `limit > 0` → formatted amount (e.g. **"$5,000.00"**) rendered as the clickable edit affordance.
- Every edit affordance carries `accessibilityLabel` "Edit credit limit for {Company}".
- The rendering difference between null and 0 is exactly D-02's contract: words ("No limit", subdued) vs numeral ("$0.00", link). They must never be visually confusable.

**Entering edit mode:** click/Enter on the affordance swaps the cell content to an `s-money-field` (label visually hidden via `labelAccessibilityVisibility="exclusive"`, label text "Credit limit for {Company}", `min="0"`, value prefilled with the current limit or empty when null) plus three buttons: **"Save limit"** (`variant="primary"`), **"Discard"** (default variant), and — only when the row currently has a limit set — **"Remove limit"** (tertiary/plain variant). Focus moves into the field.

**One row at a time:** at most one row may be in edit mode. Activating edit on another row cancels the current edit (unsaved input discarded — it is a single number; silent cancel is acceptable and keeps the one-primary-button rule intact).

**Save semantics — explicit save, never blur-save.** A limit change alters (future) checkout enforcement; it must never be committed by an accidental blur. Blur does nothing. Keyboard: **Enter = Save limit, Escape = Discard.**
- Field value empty + Save limit ⇒ save `null` (identical to "Remove limit") — clearing the field is the second path back to observe-only.
- Field value "0" + Save limit ⇒ save limit `0` (valid per D-02 — blocks all new net-terms credit once Phase 4 ships).
- "Remove limit" ⇒ saves `null` immediately, no confirmation dialog (instantly reversible, non-destructive to data). This is how a merchant returns a company to observe-only.

**Confirmed, not optimistic:** on Save limit, the field and buttons disable (in-flight); the row stays in edit mode until the server responds. On success: exit edit mode, row re-renders from revalidated loader data, toast (Copywriting rows 13–14). On failure: **stay in edit mode, keep the entered value**, show the failure as the money field's `error` text (Copywriting row 11) — the merchant retries or cancels; nothing is silently lost.

**Validation:** `min="0"` prevents negatives at input level; server re-validates. Invalid input error copy is Copywriting row 10. No maximum in v1.

**Concurrent-edit staleness:** the save request echoes the limit value the row was rendered with; the server rejects the write if the stored value has since changed (mechanism — value echo vs `updatedAt` token — is the planner's choice; the contract is the behavior). On rejection: exit edit mode, revalidate the table, show the staleness message (Copywriting row 12) as an App Bridge error toast. Last-write-wins is NOT acceptable for the limit field.

## Bypass Toggle Contract (Bypass enforcement column)

- One `s-switch` per row. Column header carries the locked label **"Bypass enforcement"** (D-03); the switch's own visible label is suppressed (`labelAccessibilityVisibility="exclusive"`), with `accessibilityLabel` "Bypass enforcement for {Company}".
- **Optimistic, immediate save on change** (Polaris switch semantics: toggles act immediately, no submit step). No confirmation dialog in either direction — the toggle is instantly reversible and the row's Status column immediately shows/hides the "Enforcement bypassed" badge, which is the real confirmation.
- While the save is in flight the switch is disabled (prevents double-fire); on success, success toast (Copywriting rows 15–16). On failure: **revert the switch to server state**, error toast (Copywriting row 17).
- Concurrency: server state wins — post-mutation revalidation syncs the switch; no staleness rejection needed for a boolean toggle (last-write-wins is fine here, unlike the limit).
- A bypassed company **keeps** its live exposure, utilization, and overdue badge (D-03: visibility without enforcement). Bypass never blanks or grays any other cell.

## Badge & Tone Semantics (Status column)

One coherent tone system, consistent with Polaris severity conventions. The Status cell shows the company's **primary state** plus, when bypassed, the bypass badge — never more than two indicators.

| State | Condition | Rendering | Tone rationale |
|-------|-----------|-----------|----------------|
| Overdue | company has an overdue balance (ledger fact — shown regardless of limit or bypass) | `s-badge tone="critical"` **"Overdue"** | Money is late — the highest-severity fact on the page |
| Over limit | `limit ≠ null` AND `exposure > limit` (includes limit 0 with any exposure) | `s-badge tone="warning"` **"Over limit"** | Serious but one notch below late money; keeps critical unmistakably = overdue |
| Within limit | `limit ≠ null`, not overdue, not over limit | subdued `s-text` **"Within limit"** — NOT a badge, NOT success-toned | Factual ledger statement. **Honesty rule: no "protected"/"enforcing" language or success tone anywhere in Phase 3 — the enforcement Function does not exist until Phase 4.** "Within limit" stays true after Phase 4 ships, so it never needs rewording. |
| Observe only | `limit = null` | subdued `s-text` **"Observe only"** | The honest CRED-04 default state; deliberately quiet — most rows on a fresh install look like this, and quiet is correct |
| Enforcement bypassed | `bypass = true` (appended after the primary state) | `s-badge tone="attention"` **"Enforcement bypassed"** | "Attention without alarm" — visible highlight, below warning severity; a deliberate merchant choice, not a problem |

Priority when stacking: primary state first (Overdue > Over limit > Within limit / Observe only), then the bypass badge. Example: a bypassed overdue company shows `[Overdue] [Enforcement bypassed]`.

Verify `s-badge` tone value names against the live catalog at scaffold time (hard rule 4); the semantic mapping above (critical/warning/attention) is the contract, the exact enum strings are indicative.

## Value Rendering Contract (Exposure, Credit limit, Utilization)

| Field | Rule |
|-------|------|
| Currency format | All amounts in **store currency**, formatted with `Intl.NumberFormat` (shop locale, `style: "currency"`, shop currency code) — grouping separators always ("$12,450.00", never "$12450"). One formatter shared by Exposure and Credit limit. |
| Exposure | Formatted amount. Negative exposure (net credit) renders as the formatter's negative form and counts as within limit. When the company's data is incomplete (`data_complete = false` — any UNRESOLVED-attribution order, D-04), append subdued suffix **"· incomplete"** wrapped in `s-tooltip` with text: "Some orders for this company couldn't be fully matched yet. This balance may be incomplete." — the visible cousin of the metafield's `data_complete` flag. |
| Credit limit | See Inline-Edit display mode: "No limit" (subdued words) / "$0.00" / formatted amount. |
| Utilization | Shown **only when `limit > 0`**: `round(exposure / limit × 100)` as a whole-number percentage ("42%", "138%"). Values above 999% display as **">999%"**. When `limit = null` or `limit = 0` → em dash **"—"** (subdued) — division is undefined; the Status column carries the meaning (Observe only / Over limit). Never color the percentage; severity lives exclusively in the Status badge. Negative exposure with a positive limit → "0%". |
| Long company names | Wrap, never truncate (data integrity over tidiness; rows may grow taller). In the narrow-screen list variant the company name is the primary slot and wraps there too. |
